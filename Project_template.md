## 2. Сравните модели эмбеддингов (локальные Sentence-Transformers vs облачные OpenAI Embeddings):
| Критерий | Локальные Sentence-Transformers | Облачные OpenAI Embeddings |
|---|---|---|
| **Скорость создания индекса** | Зависит от локального GPU/CPU: на GPU (A100, H100) можно обрабатывать 1–10 млн документов в час; легко параллелится, нет внешних rate limit | Ограничена rate limit API (обычно 3–10 тыс. запросов/мин для больших объёмов); создание индекса на миллионах документов может занять часы/дни |

- **Локальные Sentence-Transformers** выгодны при больших объёмах данных, жёстких требованиях к приватности/GDPR, но требуют вложений и инженерной экспертизы.
- **OpenAI Embeddings** оптимальны для старта, небольших и средних проектов, когда важна скорость внедрения и отсутствие инфраструктурных забот, однако растут затраты на API при масштабировании.

## 3. Сравните векторные базы ChromaDB и FAISS:

| Критерий | ChromaDB | FAISS | Qdrant |
|---|---|---|---|
| **Скорость поиска** | Высокая (HNSW), достаточна для средних объёмов; немного уступает FAISS на миллионах векторов | Очень высокая, особенно на GPU и с оптимизированными индексами (IVF-PQ, HNSW); лучший выбор для миллиардов векторов | Очень высокая, сравнима с FAISS; использует HNSW с оптимизациями на Rust, хорошо масштабируется горизонтально |
| **Скорость индексации** | Средняя: HNSW строит граф при добавлении, автоматизирован, но может замедляться на больших объёмах | Высокая при правильном выборе индекса: плоские добавляются мгновенно, IVF требуют обучения, гибкость управления | Высокая: асинхронная индексация, эффективная реализация HNSW на Rust, поддерживает массовую загрузку |
| **Сложность внедрения** | Низкая: `pip install chromadb`, простой API, встроенная персистентность, несколько строк для старта | Высокая: библиотека, требует написания обвязки, выбора индекса, сериализации, нет встроенного сервера | Средняя: требует запуска сервера (Docker/K8s) или использования Qdrant Cloud; API простой и документированный |
| **Сложность поддержки** | Низкая: автоматическое управление индексом, меньше кода, обновление данных упрощено | Высокая: экспертные знания для выбора параметров, переобучения индексов, ручная оптимизация | Средняя: нужен мониторинг сервера, бэкапы, обновления; но есть готовые Helm-чарты, managed-сервис снижает нагрузку |
| **Удобство в работе** | Высокое: встроенные метаданные, фильтрация, клиент-серверный режим, документация для быстрого старта | Низкое: только поиск по векторам, метаданные и фильтры нужно реализовывать самому | Высокое: богатый REST/gRPC API, поддержка payload и фильтров, дашборд, SDK для популярных языков |
| **Стоимость владения (учёт инфраструктуры)** | Низкая: open-source, работает на обычном CPU, минимальные требования для средних объёмов | Низкие прямые затраты (open-source), но для максимума производительности могут потребоваться GPU и дорогие специалисты | Средняя: open-source бесплатен, но для production нужен выделенный сервер (или платный Qdrant Cloud); горизонтальное масштабирование требует нескольких узлов |

---

- **ChromaDB** — лучший выбор для быстрого прототипирования и небольших проектов: минимальный порог входа, всё «из коробки», низкие затраты.
- **FAISS** — инструмент для максимальной производительности и контроля, когда есть экспертиза и нужно выжать максимум на специфическом железе (включая GPU).
- **Qdrant** — сбалансированное решение для продакшена: высокая скорость, удобный API, фильтрация, горизонтальное масштабирование. Подходит для средних и крупных проектов, где нужна надёжность и производительность без сложностей FAISS.

**Вывод:** 
* Для QuantumForge с целью "создание масштабируемого решения" оптимальнее использовать Qdrant.
* Для учебного проекта будет импользоваться ChromaDB.
